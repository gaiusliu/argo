## code-review 技能改进案例：跨 DEC 设计变更导致的审查问题消解

### 案例：doubao-seed-2.0-code-问题 5 — Ratio×Len 取整方式

#### 1. 审查时的问题（有效发现）

doubao reviewer 发现：`postProcess` 原设计中 `Ratio` 是 `float64`，`Ratio × Len` 乘积后取整方式（floor/ceil/round/truncate）未在任何文档规定，不同取整会导致截断位置差 1-2 字符。这是一个**真实存在的设计盲区**。

#### 2. 后续设计变更（DEC-010）

在 code-review 完成后，用户决定将 `Ratio` 从 `float64` 改为 `int`（百分点 1~80）。公式变为 `len × Ratio / 100`——Go 整数除法天然向下取整，**原问题的取整歧义完全消解**。

#### 3. 进一步分析发现

在更新 test-review 文档时，又发现原方案中"至少保留 1 字符"的约束在 `MaxOutputChars = 50000` 触发阈值下永不可能触发（Ratio 最小 1% 时保留至少 500 字节），同样是伪命题。

#### 4. 对 code-review 技能的启示

**当前 code-review 流程的盲区**：reviewer 在审查时刻（时间点 T1）基于当时的 task 文档和 DEC 作出判断。但用户可能在审查完成后引入新的 DEC（时间点 T2）改变设计前提，导致某些审查问题自动消解。目前流程中**没有机制追踪"跨 DEC 变更对已有审查结论的影响"**。

**建议改进**：
- 在 gen-test 回应阶段增加一行检查：如 task 文档的依赖 DEC 清单在审查完成后有新增/变更，重新评估已有结论是否需要调整
- 在 pilot 暂停确认点（④/⑦）增加一项提醒："自 code-review 完成以来，以下 DEC 已变更：[清单]，相关审查问题的前提条件可能已失效"
- 在 test-review 报告的"已过滤"类别中增加"前提条件已变更"分类，用于追踪因后续设计决策而自动消解的问题
