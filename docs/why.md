# Argo 为什么存在

## 背景

Vug 和叩问都在构建 AI Agent 能力——Vug 需要 Agent 驱动技术知识的开采、沉淀、选型和检索，叩问需要 Agent 驱动五阶段结构化教练会话。但目前两者都依赖外部 Agent 框架（如 Claude Code）提供核心循环、工具调用和记忆管理。

这种依赖带来三个问题：

- **不可控**：外部框架的 Agent 循环行为是黑盒。叩问的阶段 ④ 要求 Agent "只能追问、不得给答案"，Vug 的 learn 流程要求 Agent 按指定步骤切换上下文——这些精确的行为约束在外部框架中无法保证
- **不可独立部署**：叩问的微信小程序后端需要一个常驻的 Agent 服务进程，Vug 用户需要在终端中直接运行 Agent 流程——这两种场景外部框架都无法同时满足
- **重复建设**：工具管理、API Key 管理、记忆存储是每个 AI Agent 应用的通用底座。Vug 和叩问各自实现一套，浪费且难以统一维护

Argo 的目的：抽取 Vug 和叩问对 Agent 框架的最小公共需求，提供一个极简、可独立部署、两种交付形态的 AI Agent 运行基座。

## 目标用户

- **Vug 用户**：通过 CLI 模式在终端中运行 Vug 的 learn/select 等流程，Argo 提供 Agent 循环和工具调度
- **叩问用户**：通过 Gateway 模式让微信小程序后端连接 Argo 服务端，Argo 驱动五阶段教练会话
- **第三方 Agent 应用开发者**：任何需要极简 Agent 框架来编排 LLM 调用 + 工具执行 + 记忆存储的场景，都可以在 Argo 上扩展

## 核心价值主张

**五个模块，两种形态，无限扩展。**

Argo 不做大而全的 Agent 框架。它只做五件事——管理工具（deck）、驱动循环（helm）、存储记忆（vault）、接入模型（keychain）、加载技能（talents）——且每件事都做到接口干净、可替换。

在此之上，它同时支持两种产品形态：

- **CLI 模式**：`argo run`，在终端中直接使用，工具在本地进程内执行
- **Gateway 模式**：`argo serve`，作为 RPC 服务端常驻，供远程客户端连接

Skill 由上层应用以 Markdown 文件定义，Argo 只负责加载和执行调度。这意味着 Argo 本身不绑定任何业务场景——Vug 的 learn 是一个 Skill，叩问的五阶段教练是另一个 Skill。

## 范围

### 范围内

- 工具的注册、发现、调用，支持 CLI 本地工具和 MCP 协议工具接入
- 大模型对话的核心 Agent 循环（用户输入 → 模型调用 → 工具执行 → 结果返回 → 循环）
- 长期记忆的存储与检索，支持会话间上下文延续
- 多模型 API/API Key 的统一管理和调用路由
- Skill 的定义、加载和执行调度
- CLI 形态：本地终端可执行程序
- Gateway 形态：RPC 服务端，支持远程客户端连接

### 范围外

- 不实现大模型本身
- 不提供任何内置 Skill 的具体业务逻辑（Skill 内容由上层应用定义）
- 不实现 GUI 界面（叩问的小程序界面由叩问自己实现）
- 不实现多租户、权限、计费等 SaaS 能力
- 不做工具市场、Skill 市场的分发机制
- 不做对话流式输出的前端渲染（由客户端自行处理）
