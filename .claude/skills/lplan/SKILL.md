分层计划技能。STRUC（架构级）或 SCOP（方向级）变更时使用，分两层递进确认：

- **Layer 1** — 架构/模块级：哪些模块受影响、模块关系怎么变、数据流怎么变、前提假设、范围边界
- **Layer 2** — 接口/交互级：关键接口签名、核心数据结构、关键流程步骤

Layer 2 确认后进入 manual 逐步生成代码。代码完成后提醒用户触发 grow-doc 做迭代闭环。

## Process

### 1. 判定级别

对话中用户描述变更意图后，按全局 CLAUDE.md 中的分类标准判断级别：

- INTL / SURF — 告知用户级别，直接讨论，不启动 lplan
- STRUC / SCOP — 告知用户级别，建议走 lplan。用户确认后进入 Step 2

### 2. 分配迭代编号

列出 `docs/iterations/` 下已有目录，取下一个可用 NNN（三位数字），向用户确认迭代短名（用于目录名 `NNN-short-name`）。

如果变更不需要新建迭代（如对进行中迭代的 STRUC 变更），直接使用已有迭代目录。

### 3. Layer 1：架构/模块级

基于用户描述和代码库现状，输出以下内容：

- **受影响模块** — 列出所有受影响的模块及其变更角色（新增/修改/删除/不变但依赖）
- **模块关系变更** — ASCII 图展示模块间调用/依赖关系的变化
- **数据流变更** — 关键数据的路径变化（从哪里来、经过哪里、到哪里去）
- **前提假设** — 以 ⚠️ 标记每一项可能出错的前提条件。这是 Layer 1 最重要的部分
- **范围边界** — 明确不在本次变更范围内的内容

写入 `docs/iterations/NNN-name/main.md`，结构：

```markdown
# NNN：标题

## Layer 1：架构设计（确认于 YYYY-MM-DD）

### 受影响模块
### 模块关系变更
### 数据流变更
### 前提假设
### 范围边界
```

等待用户确认。用户确认后进入 Step 4。

如果用户对前提假设或模块划分提出质疑，修正 Layer 1 内容后重新确认。不要让有疑问的设计进入 Layer 2。

### 4. Layer 2：接口/交互级

基于 Layer 1 确认的架构，输出以下内容：

- **关键接口/函数签名变更** — 列出将被修改的函数签名、方法签名、接口定义
- **核心数据结构** — 新增或变更的关键 struct/type 定义
- **关键流程步骤** — 用伪代码或编号步骤描述核心逻辑流程

追加到同一 `main.md`：

```markdown
## Layer 2：接口设计（确认于 YYYY-MM-DD）

### 关键接口变更
### 核心数据结构
### 关键流程
```

等待用户确认。用户确认后进入 Step 5。

如果在 Layer 2 发现设计无法兼容 Layer 1 架构，回到 Step 3 修正。

### 5. 进入 manual 代码生成

告知用户分层计划完成，可以开始逐步生成代码。manual 模式中：

- 按 Layer 1 的范围边界约束范围
- 按 Layer 2 的接口设计实现
- 生成过程中发现新的 STRUC/SCOP 变更 → 回到 Step 1 重新判定

### 6. 代码完成后

提醒用户触发 grow-doc 做迭代闭环（更新模块 design.md、architecture.md 等）。

## 原则

- **前提假设是 Layer 1 的核心产出**。宁可多列几个可能错的假设，也不要漏掉
- **不在 Layer 1 讨论接口细节，不在 Layer 2 讨论实现细节**
- **用户确认前不进入下一层**——但允许用户主动说"这个我还不确定，先继续"
- **lplan 不做实现计划，不做文件清单**——那是代码生成阶段的事
